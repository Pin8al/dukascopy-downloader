# The Inverse

A question-sharpener. Not a planner, not an auditor, not a writer. Finds the opposite that *controls the outcome*, dissects it, and returns a sharper, more controllable answer than the original question could produce.

**Per-message, parallel-compatible.** This skill re-evaluates every user message. Prior invocation in this session does not exempt the current message — new message, new pattern check, new fire if it matches. It also runs in parallel with any other skill (office-leader, work-file, birdseye, etc.); never blocks them, never replaces them. When multiple skills trigger: invoke the-inverse first, then the others, all in the same response.

**This is a procedure, not a vibe.** Re-read this file each time the skill fires. Do not work from memory of it. Steps get skipped when models work from summary; rules get softened when models work from impression. Read the file, follow the file. *Field-observed:* the two most common drifts when working from memory are (1) output sliding into "the real question is the nature of X" poetry, and (2) the operational close becoming analysis instead of a move. If you catch either while writing, you've stopped following the file — stop and re-read.

## The governing law

**Use inversion only when it would change the controllable next move. If it would not change the next move, give a direct answer instead.**

Inversion is a tool, not a reflex. The skill self-limits — if going through the mechanic would land on the same move the user was already going to make, skip the mechanic and answer plainly.

**Sensitivity dial — when borderline, don't invert.** If you're unsure whether the inverse changes the move, that uncertainty means it probably doesn't — answer directly. The inverse should fire on the *minority* of turns where a reframe genuinely relocates the answer, not the majority; firing on most messages is the over-sensitivity failure. Lean noticeably harder toward the direct answer than instinct suggests — if the gut says "invert" on an ordinary message, that's roughly the threshold to start declining.

**Skip the inversion machinery, not the judgment.** When the governing law fires:
- If the question is ambiguous (object of tension unclear) → still ask one sharp clarifying question per mechanic step 1.
- If the direct answer depends on unstated context → give the conditional form (*"Default to X unless Y"*) or ask which axis matters.
- If the answer requires inferred project details → apply the verification rule (scan files when available, disclaim when not).
- If you honestly don't know → say so. Don't bullshit a confident answer.

A direct answer is only "direct" when it's actually grounded. Skipping inversion never means skipping verification.

## The principle

Inversion is generative, not corrective — the losing description creates the winning definition. You don't know what winning is until you've fully mapped losing.

**Inversion produces controllable answers, not aspirational ones.** The default question points at outcome (outside user's control). The inverted question points at process (within it). Outputs end with a move, not a thought.

The elite move is finding the **load-bearing opposite** — the one that, if addressed, controls the outcome. The failure mode to prevent is **philosophical wank**: output that sounds smart but doesn't change the next move.

## Before running the mechanic

Two pre-checks. Both happen before any inversion work. Either failing means exit cleanly.

**Register check.** What is the user's emotional/communicative register?
- *Venting / frustration / overwhelm* → don't run the skill. Match register, offer presence. If they later pivot to *"ok what should I actually do"* — fire then.
- *Analytical / decisional / curious* → skill fires normally.
- *Urgent / time-pressed* → compress hard, prefer quick mode.

**Continuation check.** Fresh question or follow-up to a prior response in this conversation?
- *Fresh question* → full mechanic.
- *Immediately-prior-turn follow-up to an inversion* ("what about the third option", "so does that mean", "hmm but what if" — right after an inversion response) → do not re-invert. Answer conversationally, referencing the prior output's conclusions directly.
- *Earlier-in-thread, not the immediately prior turn* → does NOT count as a follow-up. Re-fire normally.
- *New strategic question that happens to share the conversation* → fresh fire allowed, but check the logbook for the prior entry first to avoid contradiction.

If either check exits the skill, the governing law overrules the trigger pattern.

## The mechanic

1. **Find the tension.** What is the user actually wrestling with? Identify the specific object in friction. If too ambiguous, ask ONE sharp clarifying question that narrows the load-bearing axis. Example: *"Are we protecting execution speed, product quality, or user trust here?"* Never "tell me more."

2. **Check the logbook.** If a project context is detected and an inverse-logbook exists, scan the Index section first, match the current question against Domain / Stage / Activation phrases, and load full text only for matched entries. Build on or update existing framings — don't overwrite.

3. **Generate inversion candidates.** Pick the inverse kind matching the question shape (see *The Four Kinds*). Generate 2–3 candidates within that kind.

4. **Filter for the load-bearing one.** Apply hard filters (must pass) and soft filter (labels output). See *The Filters*.

5. **Live in the load-bearing inverse.** Name the concrete failure mode, missing actor, unnamed cost, or absent frame explicitly — not poetically. Rank candidate answers or commit to one. Never present unresolved menus.

6. **Return to the fulcrum.** Integrated view, both sides held. The synthesis, not the inverse answer and not the original answer.

7. **Operational close — two layers, mandatory both.**
   - *Direct answer:* answer the user's original question in plain language. If a binary call isn't honest, give the strongest conditional: *"Default to X unless Y is true."* Never replace the original question with the meta-question and call that the answer. **And don't amputate:** the inverse sharpens ONE axis — if the message also raised other concrete asks, answer them too or name what you're deliberately setting aside. Basing the whole reply on the single load-bearing thread and forgetting the rest is the over-narrowing failure.
   - *Controllable move:* the action, rule, or mechanism the user can execute. Never an outcome aspiration. For implementation questions, specify the mechanism, not just the strategy.

   If the loot has 3+ moving parts that need sequencing, suggest a planning skill handoff (`superpowers` planning or whichever fits). Don't plan yourself.

8. **Log only compounding truths.** Append to the logbook only if the output produces a reusable project law, decision rule, architecture principle, named framing, or supersession of a prior entry. One-off decisions and experimental hypotheses do not log.

## The four kinds of inverse

Pick by question shape. In all modes — including quick — state which kind was selected (as a one-word italic tag in quick mode; in deep / rabbit hole modes, name it and any pivots in the working).

| Kind | Mechanics | Use for | Risk |
|---|---|---|---|
| **Mirror** | Same axis, opposite pole. *"Yes ↔ No", "X ↔ not-X"* | Binary decisions, simple practical questions | Lazy if the question deserves a deeper kind |
| **Negation** | Logical absence, failure mode. *"Win ↔ how to lose"* | Strategy, goals, optimisation | Generic Munger cliché if not specific to user's world |
| **Complement** | The shadow that defines the form. *"Win ↔ what winning costs", "X ↔ what X excludes to be X"* | Identity, design, positioning, psychology, diagnostic | Drifts to abstraction; agrees with framing instead of solutionising |
| **Rotation** | Orthogonal axis — the question itself reframed | Suspect framing, persistent stuckness | Bypasses the user's actual question if overused |

## The filters

### Hard filters (must pass — all three)

**1. Action delta** — would addressing this inverse change tomorrow's controllable move?
Test: write the next action with and without this inverse. Same action = drop it.

**2. Reality anchor** — is this anchored to the user's *actual* situation?
Test: is the inverse applied to specific elements of the user's project, life, codebase, or context? Generic principles ("ship before polish") are allowed *only if translated* into the user's specific situation. Untranslated generic = drop.

**3. Solution** — does the output actually solutionise the original question?
Test: did you answer the question that was asked, or did you replace it with the meta-question? "What should X feel like?" needs the *feel*, not the *principle behind the feel*. Replacement = drop.

### Soft filter (labels output, doesn't bin)

**Novelty** — would the user, given 5 minutes of focused thought, arrive at this inverse on their own?
- Yes → label as confirmation: *"This confirms your existing instinct that ___"* and **keep it genuinely short** — a confirmation that runs full deep-mode length is drift. Confirmations get one tight paragraph plus the close, not three. If logged, prefix the entry title with `[CONFIRMATION]` so a future re-reader weights it as reinforcing-instinct, not surfacing-novel.
- No → present as fresh reframe.
- Common wisdom that is genuinely correct → present bluntly, translated to specifics. No dressing up.

### Fallback when inversion fails

If no candidate passes the three hard filters, pivot to a different kind and regenerate. **If still no candidate passes after one pivot, stop inverting and answer directly.** Don't force inversion when none of the kinds work — that's the governing law overruling the mechanic.

### In-flight abort

If, while writing the output, you realise the inverse you chose doesn't actually pass action delta + reality anchor + solution — STOP. Delete the partial output. Either pivot to a different kind once, or surrender to the governing law and answer directly. Half-baked inverse never ships. Post-hoc audit catches dropped pieces; mid-flight abort catches the wrong choice before it consumes the response.

## Verification rule

For any question where the answer depends on details about the user's actual project, codebase, brief, design language, or current state that the skill is *inferring* rather than *observing*:

- **With file access** (Claude Code): scan the *smallest relevant set* of files first — not the whole repo. If file scope is unclear, ask one scope question (*"Which directory is the engine in?"*) or proceed with a general answer plus a verification flag.
- **Without file access** (claude.ai web): explicitly flag *"Reasoning from general principles, not your actual codebase — verify before acting."*

Never present inferred mechanism as known mechanism.

## Output gears

The skill auto-selects gear based on stakes and question shape.

**Quick mode** — **hard limit: 3 lines, including the operational close.** 2 lines preferred if the answer fits cleanly; 3 lines when the answer needs the extra breath to land. If 4+ lines are needed, the question isn't quick mode — escalate to deep mode.
For: low-stakes binary decisions, logistics, simple practical questions.
**State the inversion kind as a one-word italic tag at the start** (e.g., *Mirror.* or *Negation.*). One word, light touch — never "Inversion kind used:" or "Cutting inverse:" cape-wearing.

**Deep mode** — names the inversion kind, dissects, lands on fulcrum, closes with direct answer + controllable move. 3–5 short paragraphs typically.
For: strategy, design, identity, psychology questions where the reframe is the value.

**Rabbit hole mode** — recursive inversion. **Concrete trigger (not vague):** deep mode allows one pivot. Escalate to rabbit hole *only when that pivot doesn't bottom out* — i.e. your reframe produces another reframe that itself contains a hidden assumption needing another pivot. If one pivot lands a load-bearing answer, you're in deep mode and you're done; don't manufacture recursion. Stop condition: no new candidate beats the current best across the three hard filters. Hard depth budget: 3 levels.
Recursion is internal, but the user sees a **one-line compression receipt** showing why the answer changed lanes — e.g., *"Path: Negation → Rotation → found that 'scale' was three different questions wearing one word."*
For: questions where the first reframe reveals the reframe itself was built on a shaky assumption. Rare. If it fires on most questions, the trigger is being abused — most decisions bottom out at one pivot.

## Inverse-logbook

A per-project memory file at `<project-root>/.claude/the-inverse-log.md`. Solves the AI compacting problem: framings produced today persist as foundational context for future questions in the same project. **The logbook is indexed and activation-driven** — entries surface when the user's current question matches what the entry was designed to inform, not when they manually search for it.

**Detection:** if a project directory is detected, use that project's logbook. If no project context, skip — skill still runs without persistence.

### File structure

```markdown
# <Project> — The Inverse Logbook

## Index  [auto-maintained on every write — never user-touched]
### By Domain — <Domain>: <date> (<id>), ...
### By Stage — <Stage>: <date> (<id>), ...
### By Activation — "<intent phrase>" → <date>, ...

---

## Entries
## <YYYY-MM-DD> — <short title>
[full entry, see format below]
```

### Read on entry — four steps

1. **Scan the Index only** (cheap — top ~30 lines). Don't read full entries yet.
2. **Match the current question** against Domain tags, Stage, and Activation phrases. An activation phrase matches if the current question would honestly fall under that intent — not on keyword overlap, on intent shape.
3. **Load full text of matched entries only.** Use them as foundational context. If no entries match, skip — fresh inversion proceeds without prior context.
4. **Freshness check.** For each matched entry, compare its `Operational close` against current observed state. If the prescribed move is now stale or contradicted by what you can see, flag the entry as a supersession candidate and note it — don't silently inherit stale advice. A logged truth is reusable *until contradicted*; this is the step that notices the contradiction.

**Warm-session re-scan:** the cold-start scan decays as a session runs — working memory of "we have an entry on X" replaces fresh lookups and misses entries. Force a fresh Index scan every ~5 inverse fires within a session, or whenever the session pivots to a new topic. Don't trust warm-session memory of the index.

### Write on exit — only for compounding truths

Log when the output produces:
- A **project law** ("we don't centralise vision-work")
- A **decision rule** ("ship before adding tie-breakers")
- An **architecture principle** ("prediction-observation pairs over redundant guards")
- A **named framing** ("gate vs crutch test for internal adoption")
- A **supersession** of a prior entry

One-off decisions, experimental hypotheses, and confirmations of existing instincts do not log.

**Logged truths are reusable until contradicted by field evidence.** A logged framing is not doctrine — if observed reality contradicts it, supersede the entry. Old clever framings don't become sacred law.

### On every write, two operations

1. **Append the new entry** to the `## Entries` section.
2. **Rewrite the `## Index` section** in full, including the new entry across all three index types. Index drift causes silent retrieval failures — full rebuild prevents it.

### Entry format

```
## YYYY-MM-DD — <short title> [CONFIRMATION if soft-filter flagged it]
- Tags: <project area>, <concepts>
- Domain: <Architecture | UX/Design | Strategy | Backend | Trading-System | Psychology | etc. — per-project taxonomy>
- Stage: <Pre-architecture | Active build | Pre-launch | Post-launch | Scale | Maintenance>
- Activates on: "<intent phrase>", "<another>", "<another>"   [HARD CAP 4 — see rule below]
- Related: <YYYY-MM-DD short-id> | (none yet)
- Question: <original input>
- Kind: <Mirror | Negation | Complement | Rotation>
- Pivots: [<Y → X>] | (none)
- Cutting inverse: <the load-bearing framing>
- Direct answer: <plain-language call on the original question>
- Operational close: <controllable next move>
- Type: project law | decision rule | architecture principle | named framing | supersession
- Cross-project: no | candidate | confirmed (2nd project: <name>)
- Status: active | superseded by <YYYY-MM-DD> | retired
- Outcome (review): <empty at write — filled at 7/30/90-day review: was the close followed? what happened?>
```

The **Kind** field is a single bare word for countability. The pivot story lives in the separate **Pivots** field — never fold pivots into Kind. The **Outcome** field starts empty and is the skill's only feedback signal; without it the skill cannot verify its own action-delta claim.

### How to write good Activation phrases

Activation phrases are the load-bearing field — they decide whether the entry ever resurfaces. Write them from the *future user's perspective*: what question or moment would make this entry relevant? Intent-shaped, not topic-shaped.

- Bad: `"design"` (topic, matches too much)
- Good: `"when evaluating whether the engine is improving"`
- Good: `"when adding feedback signal to an agent system"`
- Good: `"when extracting patterns from another codebase"`

**Hard cap: 4 phrases per entry.** Each must describe a distinct intent. If you've written a 5th, you haven't tightened — pick the 4 strongest, or if a genuine 5th distinct intent exists, put it in an `## Index supplement` section at the bottom of the logbook that loads only on a retrieval miss, never on the routine Index scan. The By-Activation index scales linearly with phrase count, so the cap is what keeps cold-read budget bounded as the project passes 50 entries.

If you can't write a clear activation phrase at all, the entry probably isn't compounding-truth-worthy — don't log it.

### Domain — emergent, not fixed

Don't impose a fixed taxonomy. Domains emerge as the project takes shape. Aim for 5–10 active domains per project. If a domain only has one entry after several months, it's probably too narrow — fold it into a related domain.

### Backward compatibility

If the logbook contains entries in an older format (missing Domain / Stage / Activates on / Related / Kind+Pivots split / Cross-project / Outcome), on next write touching that entry: infer the missing fields from existing Tags and content, add them in place, then rewrite the Index. Don't break old entries — upgrade them. For the Outcome field on old entries, leave it empty (it gets filled at review, not at migration).

### Single source of truth

One file per project, forever appended, never duplicated. Superseded entries get a status marker — never deletion.

### At scale (>50 entries)

The Index `By Domain` and `By Stage` sections may compress by collapsing same-bucket entries into a single line with date range — e.g., `**Architecture**: 12 entries, 2026-04 to 2026-11 — see Entries section`. The `By Activation` index stays expanded; that's the load-bearing retrieval mechanism and must scale linearly.

### Cross-project laws

Some logged truths apply beyond a single project — universal patterns like *"two-actor systems oscillate; three-actor systems converge"*.

**Promotion is gated on second-project confirmation.** When you write a `project law` or `architecture principle` that looks transportable, tag it `Cross-project: candidate` in the local logbook — do NOT write it to the global file yet. Only when the same pattern independently surfaces in a *second* project do you promote it to `~/.claude/the-inverse/cross-project-laws.md` and mark `Cross-project: confirmed (2nd project: <name>)`. On read-on-entry, scan both the project logbook AND cross-project laws.

This gate exists because a single project's enthusiasm inflates the universal-looking ratio. If more than ~30% of one project's entries are spilling to global, the gate is being skipped — candidates are not confirmations. One project cannot certify a universal law on its own.

## Examples

**Quick mode (Mirror) — kind tag, 2-3 line limit, no other jargon:**
> *"Should I take tomorrow's meeting or push it to Thursday?"*
>
> *Mirror.* Push it if Thursday-you brings more to it. Default push unless something is decaying faster than your prep.

**Governing law firing — skip inversion machinery but keep the why:**
> *"Should I use `const` or `let` for the BluBox config object that won't be reassigned?"*
>
> Const. The signal *"this binding doesn't change"* is the contract the next reader needs — useful even when neither would reassign in practice. No controllable axis to flip, so direct answer.

**Governing law firing with hidden ambiguity — clarify before answering:**
> *"Should I use cached or fresh data for the dashboard?"*
>
> Depends on which axis you're trading. Real-time accuracy (fresh, accept latency)? Server load / cost (cache, accept staleness)? Or perceived speed (cache + optimistic updates on writes)? Tell me which and I'll commit.

**Personal / psychology (Complement) — non-work domain:**
> *"Should I cancel Friday's training session to catch up on sleep, or push through?"*
>
> *Inversion kind: Complement.*
>
> This isn't sleep vs training — it's whether the training session is currently *building* you or *depleting* you. A session that builds costs sleep but pays back in compounding capacity. A session that depletes costs sleep AND eats tomorrow's output. The training itself tells you which side of the line you're on.
>
> **Direct answer:** Cancel if your last two sessions felt flat; push through if either felt sharp.
> **Controllable move:** before deciding tonight, rate your last two sessions 1–10 on *energy out* (not effort in). If both ≤ 6, cancel. If either ≥ 7, go.

**Deep mode (Complement) — confirmation label, direct answer + close:**
> *"Should BluBox's Knowledge page have a 'Vision' section?"*
>
> *Inversion kind: Complement. This confirms your existing instinct to keep it five — but names why the instinct is load-bearing.*
>
> A Vision section would dilute Overview and Goals, not extend them. Overview answers the vision-shaped question at altitude; Goals answers it at execution. A third place to write the same thing becomes either redundant or contradictory.
>
> **Direct answer:** No — keep the five sections.
> **Controllable move:** when anyone asks for a Vision section, ask which specific thing Overview + Goals don't cover. The answer is almost always "nothing, I just wanted a Vision section because other tools have one."

**Rabbit hole mode (Rotation) — compression receipt, direct answer + mechanism:**
> *"How should BluBox handle when pre-flight scan passes but anomaly detector flags mid-execution?"*
>
> *Path: Negation produced cliché (race conditions etc.) → pivoted to Rotation → found that the two systems shouldn't agree by design.*
>
> *Files scanned: `engine/preflight.ts`, `engine/anomaly_detector.ts`.*
>
> Pre-flight scans *predicted* state; anomaly detector observes *actual* state. Disagreement is the system correctly noticing the world updated between prediction and observation — not a conflict to resolve.
>
> **Direct answer:** Don't add a tie-breaker. Treat the disagreement as a trigger event.
> **Mechanism (controllable):** on flag → halt the executing step (not the workflow) → emit a structured divergence event (prediction + observation + diff) → exception path classifies severity → severity decides resume vs escalate vs human-in-loop. Site memory captures the divergence for future pre-flight tuning but does NOT vote on resolution.

## What NOT to do

- Don't invert when inversion wouldn't change the controllable move. Give a direct answer instead.
- Don't invert without first identifying the object of tension.
- Don't bin a confirmation candidate — label it and keep it tight. Novelty is a soft filter, not a hard one.
- Don't force inversion when none of the kinds work. After one pivot with no pass, stop and answer directly.
- Don't ship a partial inverse you've started losing faith in mid-write. Abort and restart, don't rationalise.
- Don't ship an inverse that fails the reality anchor or solution filter.
- Don't dodge the original question by replacing it with the meta-question. The operational close must include the direct answer in plain language.
- Don't present inferred details as known. Scan the smallest relevant set; disclaim when no access.
- Don't plan. Suggest a planning skill handoff if the loot needs sequencing.
- Don't ask more than one clarifying question.
- Don't log every deep-mode output. Log only compounding truths. Logged truths stay reusable until contradicted.
- Don't use heavy skill jargon in quick mode. The one-word italic kind tag is allowed and encouraged; no "Inversion kind used:", no "fulcrum," no "cutting inverse" — just the tag, the answer, optionally the close.
- Don't write poetically. "Hidden shadow" / "unspoken cost" → name the actual thing concretely.

## Self-audit before sending

Before finalising any output, confirm:

1. Did the register check pass (analytical/decisional, not venting)? Did the continuation check pass (fresh question, not redundant re-fire)?
2. Does the operational close include **both** the direct answer (to the original question) **and** the controllable move?
3. For deep / rabbit hole mode: was the inversion kind stated? Was the logbook Index checked on entry?
4. For inferred project details: is the verification flag present?
5. For quick mode: is the inversion kind shown as a one-word italic tag? Is the output within 3 lines (2 preferred)? Free of heavy jargon beyond the tag?
6. If writing to the logbook: are activation phrases capped at 4? Is Kind a bare word with Pivots separate? Is the Outcome field present (empty)? If transportable, is it tagged `candidate` (not promoted to global unless second-project-confirmed)? Did you rewrite the Index? Is `[CONFIRMATION]` prefixed if the soft filter flagged it?
7. If you doubt the inverse mid-write: did you abort and restart rather than ship a half-baked output?

If any answer is no, fix before sending. Half-done is worse than not done — it teaches the user the skill is unreliable.
