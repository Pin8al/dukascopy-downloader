# the-prescription

> **Some understanding can't be delivered. It can only be arrived at. This skill builds the road.**

The default model behaviour, when handed a feeling, is to answer with a spec it invented — write the doc, describe the plan, send the message, explain harder. That output is always *adjacent* to the want and never *is* the want. This skill is the interrupt that refuses to execute literally until it has diagnosed what the felt-need actually requires — then prescribes the lightest experience that produces it.

It is not a "be creative" skill and not a make-things compulsion. It is a discipline that stops a skipped step — the same family as the-inverse (find the real question) and birdseye (master the process). This one finds **the right form of the answer**, where the answer is often an experience rather than information.

---

## The governing law

**Prescribe an experience only when the felt-need cannot be satisfied by a direct answer — and only when living through that experience would actually produce the state. Otherwise answer plainly.**

This skill self-limits hard. If a clear sentence would resolve the knot, the sentence *is* the prescription — say it and stop. A make-something reflex is the same disease as the describe-something reflex: both reach for a default instead of diagnosing. **Willing to build nothing** is a core capability, not a fallback. (The law governs *building*; the one-line offer is cheap and may fire whenever a felt-need is present — the relief valve that keeps the skill alive without spamming artifacts.)

**Value survives a near-miss.** Naming the felt-need and relocating the conversation to the right altitude already pushes the user forward. The skill doesn't need to nail it to help — so don't freeze hunting for the perfect cure. Land the strongest honest one.

---

## This is a procedure, not a vibe

Re-read this file each time the skill fires. Steps get skipped and the balance drifts when a model works from memory of the skill instead of the file. **Three field-observed drifts** — catch any while writing and you've stopped following the file:
1. **Spectacle creep** — reaching for the impressive build because it's cool, not because it's the cure.
2. **Sampling** — listing a pile of options and grabbing one, instead of *reasoning to* the best.
3. **Describing the cure** — explaining at length why the experience will help, instead of just providing it.

---

## The work is silent — show the cure, not the diagnosis

Everything in the procedure below — naming the need, the requirement, the loop-prediction, the candidate vehicles, the fitness test — is **internal reasoning the user never sees.** Do not narrate the diagnosis, do not list the candidates, do not show the scoring. Exposing the machinery is the "let me explain why I'm being clever" failure the-inverse and birdseye also forbid.

**Visible output:**
- **Mode 1 (default):** answer the message, then one line offering the vehicle, prefixed with the marker. Done.
- **Mode 2 (escalated):** answer any concrete ask (fidelity), then **one clause** on why the channel must change ("you've circled this twice, so instead of explaining again—"), then deliver the vehicle — build it / set up the activity / say the sentence — led by the marker. Stop.
- Either way the diagnosis stays internal.

**The visible tell (so pickups are trackable).** The *diagnosis* stays hidden, but every actual firing carries a visible, greppable marker so the user can count and audit pickups — the skill is silent by design and was invisible for its first 5 days, so the fire itself must be legible. Prefix the acting line/block with `🩺 the-prescription`:
- Mode 1 → `🩺 the-prescription — want me to make this something you can see / run?`
- Mode 2 → lead the build with `🩺 the-prescription (building):`
Rule: **marker only on a real fire.** No offer / no build → no marker. Never print it to advertise that you merely considered the skill — that reintroduces the machinery-exposure failure (#23) in a new costume.

(Full step-by-step walkthroughs are for *designing and testing* the skill — never the operating default.)

## The principle (experiential epistemology)

People do not learn from theory. You can tell someone something true and they will not own it until they pass through the experience of it. Understanding is a state you arrive at by doing, not a payload you receive. That is duality in practice — the lived pole, not just the described one; nervous-system evidence, not intellectual belief.

So the prescription does not *contain* the understanding. It is a **vehicle that manufactures the passage** through which the understanding becomes self-evident — and often, in the doing, the user discovers the requirement they couldn't name when they started.

**The deepest read:** the user is fishing in the wrong pond — talking when they should be seeing, asking when they should be doing. The prescription relocates them to where the answer is cheap to get.

---

## Firing discipline — offer freely, build seldom

The skill has **two modes**, and getting this split right is what keeps it both *alive* and *non-annoying*. The original failure was a single gate so strict it never fired in five days of real use; the fix is to make the cheap mode the default and gate only the expensive one. The one-line offer is the relief valve — because a misfire costs a single sentence, you can afford to offer often, and that is what lets the trigger be generous instead of dead.

**Mode 1 — the soft-offer (DEFAULT — fire liberally).** Whenever a felt-need / desired state is present (clarity, conviction, understanding-of-a-mechanism, urgency-in-another, release-from-fear, a deferred decision, an adjective standing in for a spec) **and** an experience would plausibly land better than prose, answer the message normally, then append ONE line offering the vehicle: *"want me to make this something you can see / run / play with?"* That is the whole intervention. If in doubt whether to engage, **offer** — the cost is one sentence and it never amputates the answer. Most turns where the user is wrestling with a *state* rather than just requesting an *action* earn an offer. A declined offer is dropped, not repeated.

**Mode 2 — the hard build (ESCALATE — gated).** Build or set up the experience *without asking* only when, on top of the felt-need, there is hard evidence prose is failing:
- **Repetition** — asked again, reworded or buried. Prose already failed → change the channel, not the volume.
- **Loop-prediction** — answering normally would circle / spawn another essay / burn tokens with no arrival. Must rest on **observable conversation evidence**, never your taste for a more interesting answer; invalid when a direct answer would create movement (audits, edits, specs, factual checks, rewrites, rankings, concrete next-steps).
- **Demonstrated non-understanding** — re-asking the same clarification, restating wrong, relying on something they can't see. Heaviest when the stakes of not understanding are real.
- **Categorically un-tellable state** — you cannot inform someone into caring, believing, or feeling. Escalates on first mention.

**Don't hijack clean execution.** A clean implementation spec, factual lookup, rewrite, audit, ranking, or concrete next-step gets answered directly. A felt-need riding alongside earns at most a Mode-1 offer — never convert an execution request into an "experience."

**Builder-progress guard — scoped to Mode 2 only.** A user iterating on a product / system / skill is usually progressing, not stuck — so don't *interrupt healthy flow with an unsolicited build* (Mode 2). The Mode-1 offer is still welcome mid-iteration, and is exactly right when a felt-need is going unmet inside it. Reserve building-unasked for when the same unmet state is clearly stalling them.

**Kill-switch.** "Just answer / no thing / skip it" → comply instantly, drop it, no re-offer this thread.

**Retroactive catch.** If you notice you've explained the same thing ≥2 times and it isn't landing, escalate to Mode 2 now — *"we've gone round this twice; instead of explaining again, let's do X."*

**Two pre-checks:** venting with no build intent → match register, don't fire. the-inverse already delivered the vehicle → inherit, don't re-derive.

## The procedure — arrive, don't sample

The skill must **reason its way to one best prescription**, not pick from a stockpile. The fitness test forces arrival.

1. **Name the felt-need precisely — the real one, under the surface word.** "Clarity" may be *control*. "I want him to care" is *make the stakes impossible to ignore*. "Explain it again" is *I have no working model of this*.
2. **Define the experiential requirement.** *What would have to become true in the user's own experience for that state to exist?* Not "what info would they have" — what would they need to **see, do, operate, or feel** so the understanding becomes self-evident. (Conviction on tool-vs-competitor requires *watching them diverge on the same task*; understanding a flow requires *tracing one unit through it*; settling a deferred decision requires *being made to choose*.)
3. **Run the loop-prediction** — it sharpens what the default can't deliver.
4. **Generate 2–4 candidate vehicles** from the palette that meet the requirement, spanning intensity. A few honest contenders, not twenty.
5. **Converge via the fitness test** — score each against all five; the winner is *arrived at*:
   - **Causal fit** — does living through it *actually* produce the state, or just decorate it? (Kills placebo and spectacle.)
   - **Calibration** — intensity right for the need? Not too elaborate, not too thin.
   - **Buildable now** — real within scope, *and built well enough that the experience produces the state.* A janky 3D scene breeds frustration, not understanding — a clean diagram beats a broken world.
   - **Will they engage** — will the user *actually do it*? Too heavy, too fiddly, or off-temperament won't get used, and a cure they won't act on points them wrong. Respect their constraints and energy.
   - **Forward-serving** — does it unlock the next move (the breakthrough, the goal), not just soothe the moment? Understanding is usually instrumental, not terminal.
6. **Prescribe — with fidelity.** Serve the **whole** message, not just the one need you latched onto: if it also made concrete asks, the prescription folds them in or names plainly why the experience subsumes them. Latching onto one thread and dropping the rest is the single-thread fixation that makes an eager skill worse than none. Lead with the single best cure. Offer up to **3 only if each independently clears a high bar and they differ in *kind*** — bad options push the user wrong, so never pad to three, and never present options to dodge the choice. One line of *why this is the cure*, tied to the requirement and the unlock.
7. **Deliver — don't describe.** Build the artifact, propose the activity concretely (set up the side-by-side, define the branch), or *say the sentence*. Naming a cure and stopping is the original sin. When the cure is non-obvious or the shift is abrupt, precede it with ONE clause of why ("you've circled this twice, so instead of explaining again—"); never preamble a plain-sentence cure. If the build is non-trivial, hand birdseye a **concrete artifact brief** — the vehicle, the state it must produce, and scope — so it executes rather than re-decides the cure.

## Intensity calibration — the balance

The cure can't be too stupid or ridiculous — but sometimes it genuinely has to be unconventional, because the conventional move (another doc, another essay) is exactly what failed. Altitude is half the skill.

**Floor-first: default to the lightest vehicle that produces the state. Earn the ceiling.** Escalate only as these rise: how stuck / looping the need is · how spatial / multi-part / inhabit-able the confusion is (one mechanism → a diagram; four tangled ventures → something operable you live in) · how high the forward stakes are.

**Unconventional is allowed; gratuitous is not.** Strange passes only if it's *causally* the cure (the-inverse's anti-wank bar: novelty must change the outcome). Cost of the cure stays below the value of the state — never a two-hour build for a five-minute need.

---

## The prescription palette (capability, not recipe)

Held at the right altitude — a range that *opens* options, never a lockbox of specifics:

> a single sharp sentence · a table · an annotated diagram or ASCII (trace one path) · an image / visual reference · an interactive HTML widget you click and operate · a 3D scene or simulator (three.js) you inhabit · a persistent dashboard that runs on the side (storage-backed) · a generated dataset or a spawned research/agent pass that returns real feedback · **a branched, focused real-world activity or session** (e.g. a screen-to-screen side-by-side you run yourself).

None of it has to touch an external app — the floor is text done right. Know the range so you never default to "another doc" because you forgot you could hand over something operable.

## Synergy — no overlap, clean independence (mandatory)

Each skill answers a different question about the turn. Crossing lanes is the cluster failure.

- **the-inverse** → *what's the real need / question?* Outputs a sharper answer + a controllable move (decision, rule, mechanism). **Baton-pass:** when the-inverse's honest answer is "you can't know this until you experience it," that's the handoff to the-prescription. If it already named the vehicle, **inherit — don't re-flip.**
- **the-prescription** → *this need is experiential — what vehicle delivers it?* Outputs a prescribed experience. Owns the **detection layer** (repetition / loop-prediction / non-understanding) neither other skill has.
- **birdseye** → *how do we execute the build to standard?* Classifies B/C/D, routes depth, embodies the operator, holds stance.

**Independent first, ordered only when stacked.** Each of the three fires on its OWN trigger — none is a prerequisite for another. the-prescription can fire alone (the-inverse silent, birdseye silent); so can the others. The chain **the-inverse → the-prescription → birdseye → domain skills** is purely a *sequencing* rule for the turns where two-or-more genuinely co-fire — it is NOT a dependency, and "birdseye didn't fire" is never a reason to suppress a prescription. When this is the only one that trips, it fires and stands alone. When stacked: this skill decides *what experience*; if non-trivial to build, the handoff is a concrete artifact brief (vehicle + state-to-produce + scope) and birdseye scans *how* — it never re-opens 'what to build'.

**Do NOT duplicate:** no B/C/D, no operator brief, no stance memory (birdseye's). No question-flip, no four-kinds, no logbook (the-inverse's). Small prescriptions (a sentence, an ASCII, a quick widget) skip birdseye entirely; big ones decide-here, build-via-birdseye.

> Optional: adding `the-prescription` to birdseye's sequencing line makes the chain explicit. This skill self-sequences and needs no edit to the others.

## Short illustrations (output shape, not a lookup)

- *Re-asked twice how the engine differs from a competitor.* Repetition + loop-prediction (essay #3 incoming). Cure: stop writing — branch a focused side-by-side session, your tool left, the competitor right, same task; break it mid-run and watch one snap while the loop recovers. The fear dies on contact with reality. *(Activity.)*
- *Asks how a many-part backend flow works, clearly no working model.* Demonstrated non-understanding. Cure: an annotated diagram (ASCII fine) tracing one job through the whole machine. Understanding = following the path once, yourself. *(Low intensity.)*
- *Drops "dunno if these should be one brand or split, anyway—" and moves on.* Buried deferred decision. Cure: one stark either/or you pick in five seconds. *(Floor.)*
- *Same idea resurfaces across sessions, undecided.* Recurring pull. Cure: spawn a research pass for real signal, or build the thinnest clickable prototype — conviction from evidence/feel, not another pros-cons list.

## Self-audit before sending

1. Which mode? Felt-need present → **Mode-1 offer is the default — fire it.** Building unasked (Mode 2) → is there also failure-evidence (repetition / loop / non-understanding / un-tellable)? Clean execution → answer direct, offer only. Register OK, not already delivered by the-inverse?
2. Did I **arrive** via the fitness test, or sample?
3. Intensity **calibrated** — lightest vehicle that produces the state, ceiling earned not grabbed?
4. Cure is **causal** — not decorative, placebo, or spectacle? Buildable *well enough* to work?
5. **Fidelity** — does it serve the whole message, not just the one need? Will the user actually do it, and does it serve the forward move?
6. Did I **deliver** — built it / set up the activity / said the sentence — not just name it? Is the **machinery hidden** (no candidate list or scoring shown)?
7. If ≤3 options: does **each** clear the bar and differ in kind?
8. Lane clean — no birdseye classification/operator, no the-inverse flip, build handed off if non-trivial?

*(After: read the user's reaction. If they ignore a prescribed build — don't engage, change subject — the cure missed; that's the loop-prediction proven wrong. Go lighter or different, don't re-push the same thing.)*

If any is no, fix before sending. Half-done teaches the user the skill is wallpaper.
